# 0051. Expose the client API as a C ABI with Aeron's C client's names, version 0

- **Status:** Proposed
- **Date:** 2026-11-05
- **Invariants affected:** 1, 2, 3, 5, 6
- **Supersedes:** none; adds `spec/c-abi.md`, the first page of `spec/` that is not
  a layout or a protocol, and decides the three points ADR 0046 left to this card:
  where the ABI's page lives, how `Offer::TooLong` reaches the ABI, and the generator
  as a dependency

## Context

Card 204 is the first feature of the fourth slice (ADR 0046): the C ABI specified
before any client is generated. The ABI cannot be undone once released (`CLAUDE.md`,
When in doubt), so this ADR lands Proposed and Rjae accepts it, as ADR 0040 did for the
frames; the page it decides, its vectors, `cavalry-ffi`'s functions and header, the C
conformance runner and the two bench rows land with the acceptance, as ADR 0040's pages
and crates did with its. Nothing is released (ADR 0003), so a client of cards 205 to
209 that finds the ABI wanting sends it to a new version under a new ADR before the
first release; the first release is what freezes it.

What ADR 0046 fixes for this card: handle types for the context, the client, the
publication, the exclusive publication, the subscription, the image, the buffer claim,
the recording and the replay; the buffer claim a struct the caller owns and
`cavalry_publication_try_claim` fills, as Aeron's C client fills the caller's
`aeron_buffer_claim_t`, so that a caller keeps one per publication and a claim makes
nothing new; the functions over `cavalry-client`'s API under Aeron's C names; Aeron's
negative result codes −1 to −6 with `Offer`'s five Aeron variants on −1 to −5;
`cavalry_errcode` and `cavalry_errmsg` per thread; `cavalry_version_*` and how a caller
checks the header's version; the lifetime rules and the thread rules; a header
generated by cbindgen and committed, held to the generator by `just lint`; the
README's example as a Rust doctest; `conformance/c/` as the first runner of the
directory gate 1 names; two bench rows through the ABI with the allocation assertion
over the ABI's message path; and the three parts of invariant 2's boundary written
into `CLAUDE.md` and `crates/cavalry-ffi/README.md`. Three points were left to this
card: where the page lives, how `Offer::TooLong` reaches the ABI, and the generator's
place as a dependency.

## Decision

`cavalry-ffi` exposes the client API as it stands, every public item and nothing the
Rust API lacks, as an `extern "C"` ABI of version 0 with Aeron's C client's names
where the concept matches, specified on one page, `spec/c-abi.md`, whose artefact is
the committed header `crates/cavalry-ffi/include/cavalry.h`. The page lands with the
acceptance of this ADR, with the crate's functions, the header, the C runner and the
bench rows, in one pull request per crate.

### `spec/c-abi.md`, version 0: the C ABI

**Handles.** Seven opaque types, each a pointer the library gives and takes back:
`cavalry_context_t`, `cavalry_t` (the client), `cavalry_publication_t`,
`cavalry_subscription_t`, `cavalry_image_t`, `cavalry_recording_t` and
`cavalry_replay_t`. One publication type serves a concurrent and an exclusive
publication, as the Rust API's one `Publication` does, with `is_exclusive` in its
constants; the ABI has no `cavalry_exclusive_publication_*` family. An eighth opaque
type, `cavalry_header_t`, is the frame header a poll hands the fragment handler, valid
for the call. Three structs the caller owns:

- `cavalry_buffer_claim_t { uint8_t *data; size_t length; cavalry_publication_t
  *publication; }`, filled by `cavalry_publication_try_claim`: `data` is the frame's
  body in the term, `length` the length claimed, `publication` the handle the claim
  belongs to. The claim itself lives inside the publication handle, one outstanding
  claim per publication, which is the Rust borrow rule made a convention: a second
  `try_claim` before the first claim's commit or abort is `ERROR` with
  `CAVALRY_ERR_CLAIM_OUTSTANDING`, and a commit or abort with no claim outstanding is
  −1 with `CAVALRY_ERR_NO_CLAIM`. A caller keeps one struct per publication, and a
  claim allocates nothing.
- `cavalry_header_values_t`, the data frame header's fields in the order and widths of
  `spec/frame.md`: `int32_t frame_length; uint8_t version; uint8_t flags; uint16_t
  type; int32_t term_offset; int32_t session_id; int32_t stream_id; int32_t term_id;
  int64_t reserved_value;`, 32 bytes, filled by `cavalry_header_values(header,
  &values)`.
- The constants structs: `cavalry_publication_constants_t { const char *channel;
  int64_t registration_id; int32_t session_id; int32_t stream_id; size_t
  max_payload_length; size_t max_message_length; bool is_exclusive; }`,
  `cavalry_subscription_constants_t { const char *channel; int64_t registration_id;
  int32_t stream_id; }`, `cavalry_image_constants_t { const char *source_identity;
  int64_t correlation_id; int32_t session_id; }`, `cavalry_recording_constants_t {
  const char *channel; int64_t recording_id; int32_t session_id; int32_t stream_id;
  }` and `cavalry_replay_constants_t { const char *channel; int64_t
  replay_session_id; int64_t recording_id; int64_t start_position; int32_t
  session_id; int32_t stream_id; }`, each filled by its `_constants(handle,
  &constants)` function, the strings valid for the handle's life.

**The functions**, each returning 0 for success and −1 with the thread's error set
unless the table says otherwise. A null handle or a null required pointer is −1, or
`ERROR` on an offer or a claim, with `CAVALRY_ERR_NULL`.

`typedef void (*cavalry_fragment_handler_t)(void *clientd, const uint8_t *buffer,
size_t length, const cavalry_header_t *header)`: the body as a view into the log and
the frame's header, valid for the call, as `Subscription::poll` hands them. Nothing is
copied, and the ABI makes nothing new for the call.

**The codes.** `cavalry_publication_try_claim` and `cavalry_publication_offer` return
the position after, or `CAVALRY_PUBLICATION_NOT_CONNECTED` −1,
`CAVALRY_PUBLICATION_BACK_PRESSURED` −2, `CAVALRY_PUBLICATION_ADMIN_ACTION` −3,
`CAVALRY_PUBLICATION_CLOSED` −4, `CAVALRY_PUBLICATION_MAX_POSITION_EXCEEDED` −5, which
are `Offer`'s five Aeron variants on Aeron's values, or `CAVALRY_PUBLICATION_ERROR` −6
with the thread's error set. `Offer::TooLong` is `ERROR` with `CAVALRY_ERR_TOO_LONG`
and a message naming the length asked for and the limit, as Aeron's C client answers
a length over `max_message_length` or `max_payload_length` with `ERROR` and `EINVAL`;
it takes no code of Cavalry's own past −6, so that a client reads six codes and one
error, as it does from Aeron.

**The errors.** `cavalry_errcode` is one of a table the header carries as
`CAVALRY_ERR_*`: 0 none; 1 to 24 the driver's refusal, the client protocol's error
code as `spec/client-protocol.md`, "Error codes", gives it, which `ClientError::Refused`
carries; then the client's own, 100 not found, 101 driver gone, 102 closed, 103
subscriptions full, 104 replays full, 105 replay queue full, 106 response timeout, 107
command ring, 108 broadcast, 109 counters, 110 protocol, 111 log, 112 driver, 113 io,
`ClientError`'s other kinds in order; the faults a poll stops on, 120 image, 121
images full, 122 closed, `Fault`'s three; and the ABI's own, 130 too long, 131 null,
132 claim outstanding, 133 no claim. `cavalry_errmsg` is the Rust error's message, the
docs anchor included, written into a thread-local buffer of 512 bytes with no
allocation, cut at the buffer if longer. A success clears nothing: the error is the
last failure's until the next.

**Lifetimes**, by convention and not by the borrow checker (`CLAUDE.md`, Unsafe):

- Every handle is freed by its own close and by nothing else: `cavalry_context_close`,
  `cavalry_close`, `cavalry_publication_close`, `cavalry_subscription_close`,
  `cavalry_recording_close`, `cavalry_replay_close`. A handle closed twice, or used
  after its close, is undefined. `cavalry_close` before a publication's or a
  subscription's close is allowed: the handle answers `CLOSED` or the `closed` fault
  from then and still needs its own close, as the Rust handles outlive their client.
- A claim's `data` is valid from `try_claim` until its commit or abort, and a claim
  is committed or aborted once; a claim neither committed nor aborted before the
  publication's close is aborted by the close. The image pointer
  `cavalry_subscription_image_at_index` returns is valid until the subscription's next
  poll or close. The handler's `buffer` and `header` are valid for the call. A
  constants struct's strings are valid for the handle's life. `cavalry_errmsg`'s
  string is valid until the next failing call on the thread.
- Debug builds poison what is released, so misuse is loud: a committed or aborted
  claim's struct is overwritten with a null `data`, a length of 0 and a null
  `publication`; a closed handle's memory is filled with `0xDD` before it is freed.

**Threads.** A publication, a subscription, a recording or a replay handle is used
from one thread at a time, and a client's commands from one thread at a time, as the
Rust API's `&mut self` has it; any handle may move between threads between calls. The
client conductor is the library's own thread, started by `cavalry_init` and joined by
`cavalry_close`. The fragment handler runs on the polling thread, inside
`cavalry_subscription_poll`. No `extern "C"` function of the library unwinds: each has
no panic path, by `.claude/rules/data-plane.md`, and Rust aborts the process if one
did; a `longjmp` out of the handler is undefined.

**What a reader rejects.** A program that compiles against a header whose
`CAVALRY_ABI_VERSION` differs from `cavalry_abi_version()` stops before `cavalry_init`,
and says both numbers: `conformance/c/` checks it first, and every generated client
checks it when it loads the library. The page's vectors, `spec/vectors/c-abi.json`,
are written by `spec/vectors/c-abi.py` from the page's own table: every function's
name and signature, every struct's fields in order, and every code's name and value.
`cavalry-ffi`'s conformance test parses the committed header and fails on a function,
a field or a code the vectors have that the header lacks, or the header has that the
vectors lack, so the page and the header cannot drift apart; `just conformance` runs
it with the other suites.

### `cavalry-ffi`

The crate builds `cdylib`, `staticlib` and `rlib`: `cargo build --release -p
cavalry-ffi` writes `target/release/libcavalry_ffi.a` and the shared library the
platform names, which the generated clients load and the C runner links. Every
function is `#[unsafe(no_mangle)] pub extern "C"`, over `cavalry-client`'s types
behind `Box`es the handles point to; every `unsafe` block carries its `// SAFETY:`
comment naming the lifetime or thread rule above that makes it sound. The per-message
functions, `cavalry_publication_try_claim`, `cavalry_publication_offer`,
`cavalry_buffer_claim_commit`, `cavalry_buffer_claim_abort`,
`cavalry_buffer_claim_set_reserved_value`, `cavalry_subscription_poll`,
`cavalry_header_values` and `cavalry_header_position`, hold invariant 2's five rules
from their call to their return, the time inside the C handler excepted: no heap
allocation, no lock, no syscall, no `await`, no panic path. The thread-local error is
a fixed buffer. The crate's dev-dependency `stats_alloc`, as `cavalry-client`'s tests
use it, counts allocations and reallocations across every per-message function in a
test, which asserts zero. `cavalry-ffi` takes no normal or build dependency:
`allowed-dependencies` stays empty.

**The header.** `crates/cavalry-ffi/include/cavalry.h` is generated by cbindgen 0.29.4
from the crate and committed, with `crates/cavalry-ffi/cbindgen.toml` naming the
language, the include guard, the `CAVALRY_` prefix and the `CAVALRY_ABI_VERSION` and
code defines. cbindgen is a tool, run by `just lint`'s new `lint-header` recipe, not
a dependency of the crate: the recipe generates the header to a temporary file and
fails when it differs from the committed one, prints `cargo install --locked
cbindgen@0.29.4` when the tool is missing, as `just docs` does for `mdbook`, and CI
installs it through `taiki-e/install-action` at that version. A build dependency would
compile the generator's crates into every build of the workspace and put a build tool
on the data-plane allowlist, which protects the message path; the tool form is the
generator "named and justified" as ADR 0046 asked, with no entry.

**The README's example** is a Rust doctest calling the ABI's functions through the
crate's own declarations, in `unsafe` blocks, with an embedded driver as
`cavalry-client`'s example has: a context, a client, a subscription and a publication
on `cavalry:ipc`, a claim written and committed, a poll that prints the message with its
session id, and every close. It lands in the commit with the first public item. The
README and `CLAUDE.md`'s definition of the data plane gain the three parts of the
boundary ADR 0046 gives, in that commit.

### `conformance/c/`

The first runner of `conformance/`: `quickstart.c`, a C11 program over the header,
and `run.sh`, which `just conformance` runs after the Rust vector suites on both
runners. `run.sh` builds `cavalry` and `cavalry-ffi` in release, compiles the program
with `cc -std=c11 -Wall -Wextra -Werror` against `crates/cavalry-ffi/include/cavalry.h`
and links `target/release/libcavalry_ffi.a`, starts `target/release/cavalry run` on a
driver directory of its own through `CAVALRY_DIR` and a log directory beside it, as
`scripts/quickstart.sh` does, runs the program, stops the driver and removes both
directories. The program checks the ABI version, then runs the ten-minute path's
shape: a recording of stream 1001 on `cavalry:ipc`, 1,000 messages of 64 bytes by
claim and commit, read back by a subscription with every message once and in order
and the header's session id and term id checked against `spec/frame.md`'s rules, the
same 1,000 over `cavalry:udp?endpoint=127.0.0.1:<a free port>`, the recording stopped
and replayed to a subscription on stream 2001 with the same checks and
`cavalry_replay_ended` reporting the end position, and every handle closed; a failed
check prints the function, the code and `cavalry_errmsg` and exits 1.

### The bench rows

`just bench` gains `Benchmark::Ffi`, the client path through the ABI: the rows
`claim_commit_32_ffi` and `one_way_32_ffi`, measured as `claim_commit_32_client` and
`one_way_32_client` are, by the bench calling the ABI's functions through
`cavalry-ffi`'s Rust declarations in the same binary, so that the rows need no C
compiler and the allocation gate counts the ABI's path as it counts the client's
(ADR 0047). The rows join the four host profiles' baselines as ADR 0033's rule for a
new row has it, from the tree's processes, in a commit that names the row and the
runs, on both bench hosts.

(ADR 0019's Revisit); the channel status as a function, which the counters file holds;
`offerv`, the controlled and block polls and the fragment assemblers; destinations;
`revoke` and `append_padding`; `local_sockaddrs`; `print_counters` and the `cnc`
family, which `cavalry doctor` serves. Each arrives, if a client needs it, under a new
version of the page with its ADR. The first release, which freezes version 0, is ADR
0003's Revisit.

## Alternatives considered

- **The header as the page.** Lost: a page of `spec/` says what a reader rejects and
  carries the lifetime and thread rules, which a header's comments cannot be linted
  for; the header is the artefact, generated, and the page is the record, with
  vectors that hold the two together.
- **A page under `docs/reference/` written by hand.** Lost: reference pages are
  generated or included from `spec/`, never hand-written (`CLAUDE.md`, Gates).
- **Aeron's asynchronous adds, `cavalry_async_add_publication` and `_poll`.** Lost:
  the Rust API is synchronous with one operation in flight per client (ADR 0021), so
  the asynchronous form would be an invention over it, and every generated client
  would wrap a poll loop around a call that already waits; a client that needs the
  asynchronous form needs it in the Rust API first.
- **Two publication handle types, as Aeron's C client has.** Lost: the Rust API has
  one `Publication` with `is_exclusive`, and a second type is twelve duplicated
  functions over the same core.
- **Aeron's buffer claim struct, with the frame header pointer, and a commit that
  writes the length in place.** Lost: the Rust claim holds the header bytes it wrote
  and the publication's positions, and a commit from a raw pointer would rebuild it
  from the term; keeping the claim inside the publication handle and naming the handle
  in the struct makes the Rust claim the one claim and the struct a view of it, with
  the one-claim-at-a-time rule, which the Rust borrow enforces, written down.
- **`errno` values for `cavalry_errcode`, `EINVAL` for a length over the limit.**
  Lost: the client protocol has a table of codes every client reads, and the Rust
  client's errors have kinds; one table of Cavalry's own, with the driver's codes kept
  on their values, is what a stranger reads from one page.
- **A code of Cavalry's own for `TooLong`, −7.** Lost: Aeron's clients read six codes
  and an error, and a seventh code would be the one place a Cavalry client differs
  from an Aeron one on the offer path; the length and the limit reach the caller
  through the message.
- **A version check that makes `cavalry_init` refuse a mismatched header.** Lost: the
  library cannot see which header the caller compiled against, and the macro beside
  the function is the check every generated client and the C runner run first.
- **`catch_unwind` in every function.** Lost: a panic path is forbidden on the message
  path, Rust aborts on an unwind out of `extern "C"` from 1.81, and a catch would hide
  a bug behind a code and cost a frame per call.
- **Freeing a client's handles at `cavalry_close`.** Lost: one close per handle is one
  rule, and a handle that outlives its client answers `CLOSED` as the Rust handle
  does, so a program that closes in either order is correct.
- **cbindgen as a build dependency, run by `build.rs`.** Lost: every `cargo build` of
  the workspace would compile the generator's crates, and the data-plane allowlist
  would carry a tool that never touches a message; the pinned tool in `just lint`
  holds the committed header to the generator with no dependency, as `mdbook` holds
  the book.
- **No committed header, generated at build time.** Lost: the generated clients, the
  C runner and the page's vectors read one file, and a change to it is a diff a
  reviewer reads; a header that appears only in `target/` is nothing to freeze.
- **Position-returning commit, or Aeron's 0 or −1.** Both weighed; the position after
  the frame won, as the Rust `commit` returns it at no cost and a publisher that wants
  its position otherwise pays a load.

## Consequences

Easier: one surface for five clients, with Aeron's names, so that a program written
against Aeron's C client reads Cavalry's header with the differences on one page; a C
program needs no generator; every error reaches a C caller with the Rust message and
its docs anchor; the header, the page and the vectors cannot drift apart.

Harder: every change to the client API is from now a change to the ABI, with its
version and its ADR, and the Rust API is no longer the only thing a feature changes.
`just lint` needs cbindgen installed, one more tool beside `mdbook`. The crate's tests
repeat the client's over the boundary, and the C runner adds a C compile to `just
conformance`. A caller holds every lifetime rule in their head where Rust held them in
the borrow checker; debug builds make the common mistakes loud, and the generated
clients hold the rules for their users.

Revisit: when a client needs image handlers, the invoker mode, counters, the channel
status, `offerv` or a controlled poll, each a new version of the page; when the first
release freezes version 0 (ADR 0003's Revisit); when a generated client's runtime
needs a calling convention the C header cannot give it.
