# 0012. Lay out the counters file as Aeron's counter records behind a Cavalry header

- **Status:** Accepted
- **Date:** 2026-10-11
- **Invariants affected:** 2, 3, 4, 6
- **Supersedes:** none

## Context

The counters file is the second feature of the first slice (ADR 0007) and the first
shared-memory layout Cavalry specifies, so it sets the shape every later layout
follows: a header, a creation protocol, and a table of who writes and who reads each
field. Invariant 4 wants every state transition counted in a file that `cavalry
doctor` and the control plane read without touching the data plane. Card 78's research
produced two proposed decisions that bear on it directly: ADR 0010, every peer-written
field is validated against a bound the spec names, and ADR 0011, every peer-shared hot
field gets a 128-byte slot.

Aeron's counters live in the CnC file, `cnc.dat`, behind a 128-byte metadata header
whose version field is written last and volatile, so a client knows the file is ready;
the same file also holds the command ring, the event broadcast and the error log
(`CncFileDescriptor.java`). Its counters are two buffers (Agrona's
`CountersReader.java`): metadata records of state, type id, free-for-reuse deadline in
milliseconds, a 112-byte key, a label length and a 380-byte label, 512 bytes each in
the current Agrona; and value slots of value, registration id, owner id and reference
id, padded to 128 bytes "to avoid false sharing". Aeron has no file that lists its
counters; labels and type ids are assigned at runtime by the driver and its clients,
and `AeronStat` prints whatever it finds. The per-message cost of a counter is one
relaxed add in its slot. Mapping a file needs a syscall at attach and none after.
`cavalry-shm` is one of the two crates where `unsafe` is permitted.

## Decision

One layout per file: the counters file is a file named `counters` in the driver's
directory, with its own magic `CVLYCNTR`, version and capacity, and the command and
event buffers get files of their own later. `spec/counters-file.md` is its
specification at version 0. The header is 128 bytes: magic, version, capacity, creator
pid and start timestamp, filled with magic last through a release store, so a reader
that acquires the magic sees the rest. Records are Aeron's in meaning, state, type id,
reclaim deadline, key, label length and label, at 256 bytes with a 124-byte label,
which is Agrona's record before it grew, and with the deadline in nanoseconds since the
epoch like every timestamp in `spec/`. Value slots are 128 bytes (ADR 0011) with the
value at offset 0 and the rest reserved. `counters.toml` at the repository root is the
single source of every counter, with a stable id, a name, a kind, a scope, a `doc`
sentence and a `doctor` sentence; `docs/reference/counters.md` and the Rust constants
in `cavalry-shm` are generated from it, and `just lint-counters` fails when they are
stale. A static counter occupies the record whose type id is its id. A reader runs the
checks of the spec in order, too short, not ready, magic, version, capacity, length,
changed, and the record checks id, state and label, and reports the first that fails by
name; a reader of this file has no counter to increment, so it returns the error and
`doctor` reports it. When no record is free, allocation fails with `full`,
`counters.allocation_failed` increments, and whatever needed the counter is refused.
`cavalry-shm` maps the file through `memmap2` 0.9, on its allowlist, keeps `unsafe` to
the mapping and the typed views, and proves the publication protocol with `loom` on
plain memory and the slice layer under Miri. The first two counters are
`counters.allocated` and `counters.allocation_failed`.

## Alternatives considered

- **One CnC file holding every buffer, as Aeron.** Lost: every layout would share one
  version and one magic, and remapping one buffer means remapping all. One file per
  layout gives each its own header, checks and version; the directory is the unit a
  reader attaches to.
- **Agrona's current 512-byte record with a 380-byte label.** Lost: Cavalry's labels
  are generated from `counters.toml`, a name plus a key's text, and fit in 124 bytes;
  the smaller record halves the metadata region, 256 KiB against 512 KiB for 1024
  counters. The meaning of every field is Aeron's; the sizes are Cavalry's.
- **Registration, owner and reference ids in the value slot, as Agrona.** Lost for
  version 0: they serve Aeron's client-owned counters and lookups by registration, and
  the driver owns every counter in this slice. The 120 reserved bytes can take them in
  a later version.
- **Counters defined in Rust, no `counters.toml`.** Lost: the reference page would be
  hand-written or generated by compiling, and `lint-counters` needs a source the
  Python scripts of ADR 0003 and every client language can read. TOML is that source,
  as `config.toml` will be.
- **Names as the key, no ids.** Lost: an id survives a rename and is what the record
  stores; the name is the label.
- **`libc::mmap` directly.** Lost: more `unsafe` of Cavalry's own for what `memmap2`
  wraps in a reviewed API over the same `libc`; the crate is one dependency with no
  default features to turn off.
- **Capacity as a configuration key now.** Lost: invariant 5; a constant the driver
  passes serves until a measured need, and a key needs a `why_not_default` and a
  `doctor` check.
- **Milliseconds for the deadline, as Agrona.** Lost: one unit for every timestamp in
  `spec/`.
- **A checksum over the header.** Lost, as in ADR 0010: it detects corruption but not a
  hostile peer, and the compares already run.

## Evidence

- Aeron `CncFileDescriptor.java` (the header fields, and the version written last
  with `putIntVolatile` in `signalCncReady`) and Agrona `CountersReader.java` (the
  record and slot constants, `COUNTER_LENGTH = CACHE_LINE_LENGTH * 2`,
  `METADATA_LENGTH = LABEL_OFFSET + FULL_LABEL_LENGTH` with
  `FULL_LABEL_LENGTH = CACHE_LINE_LENGTH * 6`), read on 2026-10-11 from `master`.
- `spec/vectors/counters-file.py` produced 21 vectors on 2026-10-11: eight valid
  headers and records, twelve invalid, one that pins the order of the checks.
- `memmap2` 0.9.11, `MIT OR Apache-2.0`, `rust-version` 1.65.
- Nothing measured: `just bench` does not exist (ADR 0007). The slot size is ADR
  0011's to re-measure with the log buffer.

## Consequences

Easier: `doctor` and every client read one file with one table per field; a stranger
opens `counters.toml` and sees every counter Cavalry has, with what to do about each;
every later layout copies the header, the creation protocol and the table.

Harder: a new counter is a TOML entry plus two generated files, checked by a lint; the
file costs 384 bytes per counter; a larger capacity means a driver restart; readers
must handle `not-ready` and retry.

Revisit: when a client needs to own a counter, which brings the registration id into
the slot; when a driver needs more than 65536 counters; when a layout needs a field
the table's bounds cannot express (ADR 0010).
